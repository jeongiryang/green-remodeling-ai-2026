# AI 플랫폼 아이디어 주제 도출 하네스

이 절차는 **예선에 낼 주제를 고르는 데** 사용한다. 공식 심사 기준은 `contest/요구사항.md`의 문제 이해도 20·아이디어 적합성 20·창의성 25·실현가능성 20·본선 발전가능성 15다. 아래 세부 점검은 팀의 내부 검토이며 공식 추가 요건이나 예상 심사점수가 아니다. 설계 부문의 건물 지정·에너지 설계 산출물을 이 부문에 가져오지 않는다.

## 시간과 산출물

공식 예선 마감은 2026-09-30 23:59 KST. 주제 탐색이 제출 문서 작성 시간을 잡아먹지 않도록 ① 폭넓게 발상 ② 근거가 있는 3~5개만 심층 검토 ③ 1개 선정 순서로 진행한다. 9/29에는 주제 결정을 목표로 하고, 남은 시간은 제안서·요약서·증빙과 실제 접수에 사용한다. 이는 내부 목표이며 공식 마감이 아니다.

`research/sources.json`에 실제 확인한 출처를 먼저 기록한다. `research/candidates.json`에 서로 다른 해결 문제를 가진 후보 3~5개를 작성한다. `research/comparison.md`에 후보별 비교·추천·보류 사유를 설명한다. 후보 선정은 사용자가 결정하거나 명시적으로 위임해야 하며, 그 근거를 `research/decision.md`와 `harness/state.json`에 기록한다.

## 1. 문제 공간을 넓게 펼치기

노후 건물의 **종류 × 이용자 × 그린리모델링 단계**를 조합한다. 건물은 공동주택·소규모 근린생활시설·공공시설 등을, 이용자는 거주자·소유자·관리자·설계자·시공자 등을, 단계는 문제 발견·대안 비교·시공 의사결정·운영·사후 검증 등을 살핀다. 그중 실제 사용자 행동과 의사결정의 병목이 구체적인 조합을 찾는다. 단순히 기술 이름이나 챗봇 기능을 바꾼 변형은 별도 후보로 세지 않는다.

후보는 최소한 다음 질문에 답해야 한다.

1. **문제:** 누가 어떤 건물에서 어느 순간에 무엇을 결정하기 어려운가? 현재 방식의 비용·오류·불편은 무엇인가? 근거가 관찰, 연구, 공공 통계 중 무엇인지 표시한다.
2. **그린리모델링 연계:** 이 서비스의 결과가 단열·창호·설비·운영·사후관리 중 어떤 행동을 바꾸는가? 단순 일반 건물 앱이나 에너지 정보 나열과 구별한다.
3. **데이터:** 실제 열어본 자료의 제공처, 필드·단위·범위·갱신 주기, 접근 방식, 이용조건, 누락을 기록한다. 아직 확보하지 못한 데이터는 확보한 것처럼 쓰지 말고 대체 입력이나 데모용 샘플을 분리한다.
4. **AI 역할:** 입력 → 처리 방법 → 출력 → 사용자 행동을 연결한다. 규칙·검색·계산기로 충분하지 않은 이유를 설명한다. 오류·환각·편향이 생기면 어떻게 표시하거나 사람이 확인하는지도 정한다.
5. **기존 방식:** 실제 서비스나 기존 업무 흐름을 1차 출처로 확인하고 기능 단위로 비교한다. 경쟁 서비스가 없다는 주장은 조사 없이 하지 않는다.
6. **검증:** 예선에서 보여줄 한 화면 또는 흐름도, 비교할 비AI 기준선, 본선 진출 시 구현 가능한 최소 이용 흐름, 성공·실패 판정 기준을 정한다. 에너지 절감 수치는 실측·추정·목표를 구분한다.

## 2. 근거를 추적하며 후보 작성

각 후보의 `source_ids`는 읽은 출처만 가리킨다. `evidence`에는 `problem`, `green_link`, `data`, `alternative` 네 질문별로 해당 출처 ID를 넣는다. 같은 출처가 여러 질문을 실제로 뒷받침하면 재사용 가능하지만, URL만 수집하고 내용을 확인하지 않은 출처는 넣지 않는다. 해당 출처가 **무엇을 입증하지 못하는지**도 `finding`이나 비교 문서에 적는다.

`problem_evidence`는 문제의 사실과 아직 검증하지 못한 가설을 구분한다. `data_access`는 실제 접근·다운로드 여부와 권한·결측을 적는다. `ai_input`, `ai_method`, `ai_output`, `ai_necessity`는 따로 쓴다. `verification`에는 대조 기준·샘플·평가 방식·실패 조건을 적는다. `user_flow`와 `preliminary_visual`은 예선 자료를 만드는 데 곧바로 사용한다. 자세한 JSON 형식은 `harness/DATA.md`, 설명 틀은 `harness/templates/candidate-deep-dive.md`에 있다.

## 3. 걸러내기와 비교

아래 중 하나라도 치명적이면 높은 내부 점수와 관계없이 **보류**한다. 보류의 근거와 해결 조건을 `research/comparison.md`에 적는다.

- 노후 건물·구체 이용자·그린리모델링 행동의 연결이 불명확함.
- 필수 데이터가 개인·비공개 자료뿐인데 접근 권한이나 대체 입력이 없음.
- AI가 실질적인 판단·분류·추천·설명 역할을 하지 않거나 비AI 방식과 차이를 검증할 수 없음.
- 예선 제안서에 설명할 화면·흐름과 본선 최소 구현 범위를 특정할 수 없음.
- 검증 불가능한 절감률·효과 수치를 핵심 가치로 삼음.

통과 후보의 공식 예선 5개 항목을 각각 **0~5 내부 점수**로 평가하고, 점수마다 증거와 반론을 붙인다. `status`의 100점 환산은 내부 비교 보조값일 뿐 자동 선정·수상 확률이 아니다. 점수가 비슷하면 데이터 확보와 10/24~25 본선 최소 구현의 실현성을 우선 검토한다. 비교 문서에는 최소 1개 추천, 바뀔 수 있는 가정, 추천을 뒤집을 새 증거를 적는다.

## 4. 반대 검토 후 결정

추천 후보에 대해 ① 사용자가 실제로 이 행동을 할까 ② 데이터가 안 오면 작동할까 ③ AI가 틀린 추천을 하면 피해가 뭔가 ④ 기존 서비스보다 무엇이 다른가 ⑤ 본선에서 시연 가능한가를 다시 묻는다. 약점은 숨기지 말고 축소 범위·대체 방법과 함께 기록한다. 사용자에게 후보별 차이·근거 수준·최대 위험을 제시한 뒤 주제를 확정한다.

```powershell
python scripts/harness.py check --stage ideation
python scripts/harness.py advance
```

`check`는 필드와 출처 연결·점수·비교 파일을 확인한다. 출처가 주장을 **실제로** 뒷받침하는지, 후보가 좋은 아이디어인지는 검토자가 원문을 읽어 판단한다. 검사가 통과해도 팀의 주제 선택이 자동으로 이루어지지 않는다.
